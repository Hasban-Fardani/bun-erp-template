# F3.1 — Productivity program

## Goal

Close the Laravel productivity gaps that matter for an ERP, as opt-in catalog features and packages
(never default app bloat):

1. **AI productivity pack** — project introspection for agents (MCP), `bun erp about`, aggregated
   guidelines, `bun erp ai:update`.
2. **Scheduler** — recurring jobs on the existing durable queue.
3. **Data safety** — numbering sequences, optimistic locking, soft delete.
4. **Import/export + job batching** — bulk operations with progress.

## Execution model

- **Wave A (parallel):** Phase 1 + Phase 2, each in its own `git worktree` with its own `apps/`
  install and its own verification run. Disjoint file ownership.
- **Wave B (parallel):** Phase 3 + Phase 4, same model.
- Every phase: TDD red→green, `bun erp check` green inside its worktree, evidence reported to the
  integrator (who appends it here).
- **No phase adds a runtime dependency.** MCP, cron parsing and CSV are implemented in-repo; this
  keeps merges clean and the template dependency-light.

## Migration numbering (pre-assigned, no collisions)

## Core vs opt-in (classification)

Rule (P11): **core** is cross-cutting runtime infrastructure other code depends on, with no heavy
dependency and no UI or domain semantics; everything with a heavy dependency, a UI surface or domain
meaning is **opt-in** through the catalog.

| Item | Status | Why |
|---|---|---|
| `apps/server` + `apps/web` | chosen at `bun erp init` | the combination is the user's choice; `apps/` ships empty |
| `apps/mobile` | opt-in (`apps:create`) | second client with a native toolchain |
| `packages/ui`, `i18n`, `utils`, `storage` | core | primitives every app imports |
| Better Auth identity (session, email/password, dormant Google) | core | request identity |
| RBAC (permissions, roles, cache) | core, tenant-free | every guarded route needs it |
| Audit log, notifications (database channel), durable jobs, health/ready, OpenAPI, error envelope, logging | core | cross-cutting runtime |
| **Scheduler engine** (parser, `job_schedules`, tick, lock) | **core** (P12) | infrastructure; features register their own schedules and nothing runs without one |
| **Batching** (`infra/jobs/batch.ts`) | **core** (P13) | the queue is already core and bulk operations need it |
| **Soft delete, optimistic locking, numbering sequences** | **core helpers** | cross-cutting data-safety primitives, applied by `make:feature` and the reference module |
| CLI, gates, skills, `AGENTS.md`, `bun erp about`, `bun erp mcp`, `ai:update` | core (dev tooling) | zero runtime dependency, works with `apps/` empty |
| `data-table`, `charts`, `editor`, `email`, `pdf`, `mail`, **`spreadsheet`** | opt-in packages | heavy or rendering-only dependencies |
| `departments`, `users`, `roles`, `audit`, `mail`, `organizations`, **`import-export`** | opt-in features | UI surface, permissions or domain meaning |

## Phase 1 — AI productivity pack

Deliverables:

1. `bun erp about` — one screen: Bun/TypeScript versions, installed apps, packages, features,
   migration count, route count, DB reachability, gate count, CodeGraph index state.
2. `bun erp mcp` — stdio MCP server, read-only, implemented in `cli/lib/mcp/**` with no dependency.
   Supported subset: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`.
   Tools:
   - `app-info` — the `about` payload as JSON;
   - `db-schema` — tables, columns, indexes parsed from the Drizzle schema + migrations;
   - `routes` — method, path, feature, required permission;
   - `logs` — recent structured log lines, redacted;
   - `jobs` — queued/dead/failed counts;
   - `docs-search` — local search over `docs/**`, package `llms.txt` and feature READMEs;
   - `guidelines` — the aggregated AI guidelines block.
3. Guidelines aggregation: a marked block in `AGENTS.md` (`<!-- guidelines:start -->` …
   `<!-- guidelines:end -->`) listing installed apps/packages/features with their guide path;
   `features:install` and `packages:install` refresh it.
4. `bun erp ai:update` — re-syncs the guidelines block, the CodeGraph MCP wiring and the skills.
5. Tests: MCP handshake (`initialize` → `tools/list` → `tools/call` per tool), schema parsing,
   route listing, docs search, guidelines block generation (red→green).

## Phase 2 — Scheduler

Deliverables:

1. `defineSchedule({ name, cron, handler })` in `infra/jobs/scheduler.ts`; features register their
   schedules in `features/jobs.ts`.
2. `job_schedules` table (name, cron, timezone, lastRunAt, nextRunAt, lockedUntil, lastStatus,
   lastError) + `0008_scheduler.ts`.
3. Leader-safe tick: `jobs:tick` (one pass) and a tick inside `jobs:work`; a DB advisory lock so two
   workers never run the same schedule.
4. CLI: `jobs:schedule` (list schedules with next run) and `jobs:tick`.
5. Hand-rolled 5-field cron parser (`*`, ranges, lists, steps) + next-run computation in UTC.
6. Tests: parser cases, next-run from a fixed clock, due detection, lock prevents a double run, a
   tick enqueues exactly one job per due schedule, missed runs coalesce.

## Phase 3 — Data safety

Deliverables:

1. Soft delete: `softDelete()` column helper (`deleted_at`), `notDeleted()` filter helper, and
   `restore`/`forceDelete` service helpers; applied to the `departments` reference feature and
   emitted by `make:feature`.
2. Optimistic locking: `version` column helper; update validation takes `expectedVersion`; a stale
   write returns 409 with the current version; applied to departments and emitted by `make:feature`.
3. Numbering: `sequences` table + `nextNumber(tx, key, { prefix?, padding? })` using a row lock so
   numbers are unique and gap-less per key; infrastructure only — no invented business domain.
4. `0009_data_safety.ts` (sequences table + departments columns).
5. Tests: restore/force-delete, 409 on stale version, gap-less numbering under concurrent inserts,
   generator output (scaffolding test).

## Phase 4 — Import/export + job batching

Deliverables:

1. Batching in `infra/jobs/batch.ts` (**core**, extends the durable jobs engine the way Laravel's
   `Bus::batch` extends its queue): create a batch from item keys, process in chunks, expose
   progress (processed/failed/total), support cancel and resume; `0010_import_export.ts` adds the
   batch tables.
2. Catalog package `templates/packages/spreadsheet` (**opt-in**) — tabular formats behind one
   dependency boundary:
   - CSV read/write via **`papaparse`** (exact-pinned): BOM, delimiter detection (Excel in an
     Indonesian locale writes `;`), quoted fields, embedded newlines, streaming;
   - XLSX read/write via **`exceljs`** (exact-pinned, per ADR-0005): styled headers, column widths,
     number/date formats, multiple sheets, streaming reader;
   - shared row/column types so features never import the libraries directly;
   - SheetJS stays rejected (ADR-0005 rationale).
3. Catalog feature `templates/features/import-export` (**opt-in**, `requires: ["spreadsheet"]`) —
   the pipeline, not the formats:
   - column mapping, per-row validation, dry-run report with row-level errors;
   - import runs as a batch job with progress and a cancel action;
   - export uses the data-table server contract, so a resource exports exactly what it lists;
   - web UI: export action on the resource table; import wizard (upload → dry-run → confirm →
     progress) using the data-table package and the notification channel.
4. Tests: batch progress/cancel/resume, CSV round-trip with quoted/escaped fields and `;`,
   XLSX round-trip with styles, dry-run report, export column selection.

## Decision log (new)

| # | Decision |
|---|---|
| P1 | MCP server lives in the CLI, stdio, read-only, no dependency (documented protocol subset) |
| P2 | `docs-search` is local-first (`docs/**`, `llms.txt`, feature READMEs); no network in v1 |
| P3 | Guidelines aggregate into a marked `AGENTS.md` block, refreshed by `ai:update` |
| P4 | Scheduler reuses the durable jobs table plus a `job_schedules` table; no second runtime |
| P5 | Cron parsing is hand-rolled (5-field, UTC) to avoid a dependency |
| P6 | Soft delete and optimistic locking are helpers plus generator changes, not ORM magic |
| P7 | Numbering is infrastructure (`sequences` + row-locked helper); no invented domain |
| P8 | Tabular formats live in the opt-in `spreadsheet` package: `papaparse` for CSV, `exceljs` for XLSX (both exact-pinned); SheetJS stays rejected per ADR-0005 |
| P9 | Batching extends the existing jobs table; no second queue |
| P10 | No phase adds a dependency to the default install; dependencies live in opt-in catalog packages (only Phase 4 has any) |
| P11 | Core vs opt-in rule: **core** = cross-cutting runtime infrastructure other code depends on, with no heavy dependency and no UI or domain semantics; **opt-in** = anything with a heavy dependency, a UI surface, or domain meaning |
| P12 | The scheduler engine (parser, `job_schedules`, tick, lock) is core, like Laravel's `schedule()`; no schedule is registered by default, so an install without schedules does nothing |
| P13 | Batching is core (the queue is already core); import/export is opt-in |
