# F3.1 — Productivity program

## Goal

Close the Laravel productivity gaps that matter for an ERP, as opt-in catalog features and packages
(never default app bloat):

1. **AI productivity pack** — project introspection for agents (MCP), `bun erp about`, aggregated
   guidelines, `bun erp ai:update`.
2. **Scheduler** — recurring jobs on the existing durable queue.
3. **Data safety** — numbering sequences, optimistic locking, soft delete.
4. **Import/export + job batching** — bulk operations with progress.

## Execution model

- **Wave A (parallel):** Phase 1 + Phase 2, each in its own `git worktree` with its own `apps/`
  install and its own verification run. Disjoint file ownership.
- **Wave B (parallel):** Phase 3 + Phase 4, same model.
- Every phase: TDD red→green, `bun erp check` green inside its worktree, evidence reported to the
  integrator (who appends it here).
- **No phase adds a runtime dependency.** MCP, cron parsing and CSV are implemented in-repo; this
  keeps merges clean and the template dependency-light.

## Migration numbering (pre-assigned, no collisions)

The default catalog ends at `0007_notifications`; the `departments` feature installs `0008`.
Phase migrations are written as files the phase adds to the app catalog:

| Phase | Migration file |
|---|---|
| 2 Scheduler | `0008_scheduler.ts` |
| 3 Data safety | `0009_data_safety.ts` |
| 4 Import/export | `0010_import_export.ts` |

`features:install` numbers catalog migrations at install time, so feature-owned migrations use their
own names (`migrations/<name>.ts`) and never clash.

## Phase 1 — AI productivity pack

Deliverables:

1. `bun erp about` — one screen: Bun/TypeScript versions, installed apps, packages, features,
   migration count, route count, DB reachability, gate count, CodeGraph index state.
2. `bun erp mcp` — stdio MCP server, read-only, implemented in `cli/lib/mcp/**` with no dependency.
   Supported subset: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`.
   Tools:
   - `app-info` — the `about` payload as JSON;
   - `db-schema` — tables, columns, indexes parsed from the Drizzle schema + migrations;
   - `routes` — method, path, feature, required permission;
   - `logs` — recent structured log lines, redacted;
   - `jobs` — queued/dead/failed counts;
   - `docs-search` — local search over `docs/**`, package `llms.txt` and feature READMEs;
   - `guidelines` — the aggregated AI guidelines block.
3. Guidelines aggregation: a marked block in `AGENTS.md` (`<!-- guidelines:start -->` …
   `<!-- guidelines:end -->`) listing installed apps/packages/features with their guide path;
   `features:install` and `packages:install` refresh it.
4. `bun erp ai:update` — re-syncs the guidelines block, the CodeGraph MCP wiring and the skills.
5. Tests: MCP handshake (`initialize` → `tools/list` → `tools/call` per tool), schema parsing,
   route listing, docs search, guidelines block generation (red→green).

## Phase 2 — Scheduler

Deliverables:

1. `defineSchedule({ name, cron, handler })` in `infra/jobs/scheduler.ts`; features register their
   schedules in `features/jobs.ts`.
2. `job_schedules` table (name, cron, timezone, lastRunAt, nextRunAt, lockedUntil, lastStatus,
   lastError) + `0008_scheduler.ts`.
3. Leader-safe tick: `jobs:tick` (one pass) and a tick inside `jobs:work`; a DB advisory lock so two
   workers never run the same schedule.
4. CLI: `jobs:schedule` (list schedules with next run) and `jobs:tick`.
5. Hand-rolled 5-field cron parser (`*`, ranges, lists, steps) + next-run computation in UTC.
6. Tests: parser cases, next-run from a fixed clock, due detection, lock prevents a double run, a
   tick enqueues exactly one job per due schedule, missed runs coalesce.

## Phase 3 — Data safety

Deliverables:

1. Soft delete: `softDelete()` column helper (`deleted_at`), `notDeleted()` filter helper, and
   `restore`/`forceDelete` service helpers; applied to the `departments` reference feature and
   emitted by `make:feature`.
2. Optimistic locking: `version` column helper; update validation takes `expectedVersion`; a stale
   write returns 409 with the current version; applied to departments and emitted by `make:feature`.
3. Numbering: `sequences` table + `nextNumber(tx, key, { prefix?, padding? })` using a row lock so
   numbers are unique and gap-less per key; infrastructure only — no invented business domain.
4. `0009_data_safety.ts` (sequences table + departments columns).
5. Tests: restore/force-delete, 409 on stale version, gap-less numbering under concurrent inserts,
   generator output (scaffolding test).

## Phase 4 — Import/export + job batching

Deliverables:

1. Batching in `infra/jobs/batch.ts`: create a batch from item keys, process in chunks, expose
   progress (processed/failed/total), support cancel and resume; `0010_import_export.ts` adds the
   batch tables.
2. Catalog feature `templates/features/import-export` (server + web):
   - CSV export for a resource, reusing the data-table server contract;
   - CSV import with per-row validation, dry-run, and an error report;
   - import runs as a batch job with progress and a cancel action;
   - hand-rolled CSV reader/writer (quoted fields, escapes, CRLF).
3. Web UI: export action on the resource table; import wizard (upload → dry-run → confirm →
   progress) using the data-table package and the notification channel.
4. Tests: batch progress/cancel/resume, CSV round-trip with quoted/escaped fields, dry-run report,
   export column selection.
